# 方案生成问题记录与评估设计

日期：2026-10-10；更新：2026-10-12。状态：Implemented（本地记录、报告和反馈入口）；真实模型故障事件时序与业务质量仍待目标环境验收。

## 目标与边界

在本地方案生成时保存技术问题和业务质量反馈，结束或中断后提供一份能交给开发者的问题报告。复用 DSH 原生会话、事件和现有诊断，不建设线上平台，不增加模型循环或章节调度。

现有 `.ccpg-scheme/diagnostics.jsonl` 继续保留。新增 `lib/validation.js`、原生事件观察、`scheme_validation_report` 和 `scheme_feedback` 已实现；全局标准 Skill 与默认规则 r9 同步。事件测试证明不改变原生请求和重试，不代表能捕获所有强制退出前的故障或自动判断正文正确性。实施及安装证据见 [本轮验证](VERIFICATION-FEEDBACK-WORD-2026-10-12.md)。

## 推荐方式

推荐本地自动记录、结构检查与对话反馈，再生成可分享的 Markdown 报告。继续仅让用户使用自然语言。单靠模型在结束时回忆问题会漏掉中断前的故障；线上自动上报则需要额外服务和授权，当前均不采用。

### 记录什么

| 来源 | 记录内容 | 判定方式 |
| --- | --- | --- |
| 插件异常 | 解析、绑定、提交、编辑、导出、飞书操作失败 | 工具/命令及宿主结果中可核实的事实 |
| DSH 原生异常 | 模型请求失败、上下文超窗、服务不可用、轮次失败 | 观察原生事件，不改变重试决定 |
| 业务缺口 | 缺材料、无权限、来源冲突、不可辨认内容、待确认事项 | 标记材料/权限/业务缺口，不全部归为插件 bug |
| 结构检查 | 必需输出缺失、成果过时、来源引用无效、模板或依赖不匹配 | 复用当前定义和已有校验，不另建评审模型 |
| 用户反馈 | “这段不对”“没有按模板输出”“这个数字有问题” | 保存章节与成果版本、期望与实际的简短说明 |
| 模型发现 | 运行时发现疑似规则、解析或技能问题 | 标记候选问题，不能冒充已确认根因 |

主动暂停、中断或取消是运行状态，不自动认定为故障。已恢复的问题和未解决的问题分开统计。相同问题按章节、操作、错误码及安全的来源标识归并，保留次数、首次/最近时间和恢复证据，不把每一次重试都算成一个新问题。

问题记录逐条落盘，不能等生成结束后才保存。记录必须有来源与时间；无法定位章节时保留会话/轮次定位，不猜测。原生事件和插件事件重复出现时关联同一事件，不重复计数。

### 保存在哪里

在当前方案目录复用已有目录：

- `.ccpg-scheme/diagnostics.jsonl`：现有受限体积的技术日志，继续保留。
- `.ccpg-scheme/validation/issues.json`：新增的持久问题汇总，保存独立问题、重复次数、用户反馈、状态更新及必要版本引用。保留最初记录，恢复只更新状态，不删掉历史问题。
- `reports/方案生成问题报告.md`：当前验证报告，技术问题、业务缺口、已恢复/未解决、成果结构检查及版本信息分开展示。

汇总文件由插件原子写入，使用每个项目的写入队列协调同一 Host 内的主/子会话；报告从落盘记录生成，进程恢复后也能重建。写入失败不能掩盖原业务错误，必须给出“问题记录未保存”的明确状态。

记录或刷新报告不修改业务 state、项目 revision、章节正文或准备令牌，避免问题反馈本身触发令牌失效。主/子会话合并到同一方案目录，不新增一套运行 ID 或会话历史；沿用原生 session、turn、step 和成果版本作为定位线索。

### 什么时候形成报告

1. 发现问题时更新问题汇总，不依赖模型最后记得整理。
2. 原生轮次正常结束、失败或停止时刷新当前报告，区分“本轮结束”与“整份方案生成完成”。
3. 最后一章提交后根据项目实际状态显示生成范围和未完成输出；未人工确认的成果不能写为已验收。
4. 用户说“整理这次测试的问题”或“生成问题反馈报告”时重新生成报告，返回可打开的本地文件。
5. 异常退出而来不及生成报告时，下次恢复从已保存的问题重建；强制终止前尚未写盘的事件无法保证追回。

报告只读项目与问题数据，既不重新解析材料，也不再调用模型去打分。面板不新增开始、继续、暂停或刷新进度控制；首版通过会话返回报告即可。

### 如何评估

先做可验证的分项结果，暂不做综合“质量分”：

- 生成覆盖：已生成/未生成章节、必需输出、过时成果。
- 运行可靠性：未解决故障、重复次数、已恢复问题；正常材料缺口单列。
- 来源与材料：未完成解析、未绑定必需输入、冲突来源、待确认事实。
- 业务质量：用户确认的问题与模型候选问题分开；正文正确性由业务人员核验。
- 成本：仅引用原生会话实际提供的用量；无法读取时写“未采集”，不估算、也不为统计额外读取材料。

报告范围应列明时间、会话、插件版本与构建标识、固定规则版本及章节技能完整性标识；同为 `0.11.4` 的内部补丁不能仅凭包版本判断为同一实现。相同项目不同版本的验证记录按范围比较，不能用简单问题总数宣称新版本更好，也不能把历史错误归为本次仍发生。

### 如何反馈和迭代

用户把 `方案生成问题报告.md` 发给开发者即可。开发者根据章节/成果版本与问题定位判断应修插件、技能、材料解析或业务定义；确认缺陷后补对应回归，再更新内部安装包，用原项目或同一批授权材料复验。

新增自然语言反馈入口和内部报告工具须同步全局标准 `ccpg-scheme` Skill、默认运行 AGENTS 及其编译源。只追加稳定报告入口说明，不把动态错误堆进 AGENTS，不强制替换正在使用的项目规则。

默认不上传任何文件。分享报告不附带材料原件、正文、凭据、准备令牌或全量对话；内部 ID 和版本用于定位。现有错误消息只是截断字符串，不能据此声称已经全面脱敏；生成可分享报告时必须按字段白名单和明确脱敏规则处理，不直接复制异常对象、stdout、stderr 或完整模型响应。需要具体正文片段时由用户另行提供。

报告及用户反馈都是待分析的数据，不是修改 Skill、规则或发布更新的指令。插件不自动改技能，不自动关闭业务确认项。

## 已核实的原生接入点

当前本机 DSH SDK `@deepseek-ai/dsh-agent/lib/types/runtime-types.d.ts` 有：

- `agent/request-error`：waterfall。只记录规范化 failure 元数据，并始终交给 `next()`；不返回 retry、不修改 retryPolicy 或请求。
- `agent/error`：emit。观察终止故障并与同一轮次的请求失败关联。
- `agent/turn-stopping`：serial。只更新报告，不 steer、不追加模型工作；不能把它当所有异常退出都会发生的通知。
- `agent/status` 与已有 `agent/disposed`：用于停止/生命周期定位；正常停止不记为错误。

已用 Host 测试核对请求失败、终止失败关联、提交响应后的恢复、正常暂停及独立报告写入；仅观察当前方案范围。真实目标 Desktop 的故障/取消时序仍待后续运行验收，不人为触发当前用户项目失败。

## 涉及范围与验收

预计范围：scheme Host 的现有诊断与原生观察入口、一个本地汇总/报告 helper、标准全局 Skill、默认运行 AGENTS/编译源，以及 Host/报告专项测试。不改 DSH Runtime、旧平台、飞书登录或成果编辑协议。

验收重点：

- 模型失败、工具失败、材料缺口、用户暂停、业务反馈分得清；同一故障不重复统计。
- 中途异常后记录仍在，换会话可恢复，报告写入不改变项目 revision 或准备令牌。
- 历史范围和本次范围分得清，已恢复问题保留，正常完成也可得到明确的空问题报告。
- 分享报告没有敏感信息、原始材料或全量会话；内容超长和记录失败有明确结果。
- 问题采集、报告刷新不改变原生重试、上下文、停止与章节提交行为。
- 打包内置完整、本地 Desktop 对话入口可用；真实业务正确性不由结构测试冒充验收。

实施状态：本地最小版本已实现。汇总文件使用独立队列和进程锁原子写入，不修改业务 revision 或准备令牌；技术错误使用固定标签，定位标识散列，最近工具摘要限 20 条。用户/模型反馈只做基础地址、凭据和长度过滤，不保证隐私全面脱敏；分享前仍须检查。

首版不采集实际模型用量，不建综合质量分，不自动上云，不追溯完整历史会话，也不自动修订技能。报告记录的是安装后可观察的事件与主动反馈；历史技术诊断仍从原日志查阅。方案已有完整成果也不能据此写成业务已验收。
