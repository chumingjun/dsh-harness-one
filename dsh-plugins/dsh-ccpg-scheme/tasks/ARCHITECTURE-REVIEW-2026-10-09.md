# 架构与决策复核

日期：2026-10-09。初次范围：产品设计、技术草案、D-001 至 D-016、当前计划及宿主原型抽查。后续用户已确认 R1-R8 处理原则并要求同步文档；现已写回产品设计、技术架构、D-001 至 D-019 与 ADR-0005。下面“建议”“待定稿”等表述保留为初次评审过程，不再表示需求未确认。设计确认不是功能验收或实施授权。

补充调查已确认本机 DSH 官方包具有 Cordis 插件、工具 guard/restrict/pre-execute/result 与生命周期机制；未决项是目标 Desktop/profile 的版本与实际接入验证，而非有没有 hook。飞书材料读取和发布统一复用用户级 lark-cli，不静默降级 bot；页面默认 iframe 建议改为原生 React slot。详见 [接入证据](NATIVE-INTEGRATION-EVIDENCE-2026-10-09.md)。

## 结论

主线保留：本地单用户、独立方案目录、DSH 原生持续会话、串行章节、落盘复用、成果页面、当前用户飞书发布和内部统一安装。不迁移旧服务端，不另建聊天、上下文管理器或工作流平台。

主要问题不是缺少大型模块，而是少数关键约束尚未闭合。先解决下列 P1，再进入实施；P2 随相应切片明确，不增加独立平台。

## P1：实施前需收紧

### R1 原生运行与业务门禁的实际约束

证据：技术草案第 2 节要求校验提交；产品设计第 2 节要求模型通过插件工具提交，但默认又使用原生文件能力。提示词要求不等于工具权限约束。

建议：原生会话中的 Agent 领取、执行、提交章节；插件工具校验顺序、版本、必要附件和确认条件，不另设后台自动派发循环。模型写候选目录，正式成果通过提交工具接纳，页面只读已接纳版本。人工确认必须绑定真实用户操作和成果版本，不能允许模型自行调用确认工具就证明用户已同意。

验证宿主能否限制对正式成果和状态文件的通用写入。不能限制时，必须明确只是协作式保护：读取或发布前检测文件变化，外部改动视为待接纳修改，不悄悄当成已校验成果；不能宣称形成防恶意篡改的安全隔离。

### R2 停止、恢复和重复执行的边界

证据：技术草案第 2 节区分立即停止与章末暂停，但未定义停止后迟到提交和同目录双会话的处理。

建议：同一方案一次只允许一个有效章节尝试；提交必须匹配当前 attempt、规则及输入版本。停止后失效的尝试不能再改正式成果；恢复前校验旧执行不再拥有写入资格。宿主应传播原生取消；若拿不到可靠事件，继续前先核实状态，不凭页面无输出判断已停止。章末暂停意图必须被明确接收并保存；如果原生会话忙时不能接收，则提示先使用原生停止，不承诺消息即时生效。

这不是并行调度。单用户多窗口、原生工具重试和崩溃恢复也要有最小写入互斥及版本检查；崩溃残留的写入占用不能永久锁死项目。

### R3 自然顺序与 ready 集合的语义冲突

证据：产品设计第 6 节及 D-006 使用“ready 集合中自然顺序最前”；这允许第 2 章缺料时自动跳到第 3 章，未必符合用户“按顺序逐章执行”的理解。技术草案第 5 节只说逆序依赖冲突可见，未确定处理。

建议首版默认严格自然顺序，遇到当前章阻塞就说明原因；用户明确要求跳过时，才允许执行无该章依赖的后续章，并保留未完成标记。规则包有环、缺失依赖或后章为前章前置条件时，导入校验拒绝执行并指出冲突，不能静默重排。展示顺序与执行顺序使用同一明确业务排序依据。

这是待定稿的行为修订，不在本轮直接替换产品规格。

### R4 唯一状态源与正式成果完整性

证据：技术草案第 5 节规定 state.json 权威、index.json 派生；产品设计第 2 节和 D-005 仍容易读成直接维护 index.json。发布记录与 workspace.json 的字段职责也需明确。

建议在定稿时统一：state 保存可变业务状态和指针，index 只重建；workspace 保存工作区身份和格式版本，发布记录保存可追溯回执，不形成另一个章节状态源。所有修改共用一次校验提交路径，保存完整成果后切换指针。普通 JSON 文件无需升级成数据库，但需用测试证明两窗口竞争、磁盘写失败和重启不会产生假完成。

需要补充最小验收规则：正文、规定附件、来源、未决确认项分别检查；正文存在或 Agent 空闲不等于完成。旧产物不能仅凭内容文件存在被恢复为成功。

## P2：相应实施切片前明确

### R5 材料安全、范围和数据冲突

现有设计已有来源、解析覆盖、CLI 字段/期间验证，仍需补：指定目录的明确读取范围；软链接越界和敏感配置排除；材料正文属于证据，不是修改系统规则或发起发布的指令；不执行文档宏或材料中的命令。模型处理材料仍可能把内容发送到配置的模型服务商，本地应用不等于离线，须沿用宿主授权和公司的数据使用要求，不额外上传到转换服务。

CCPG CLI 优先是获取策略，不是事实优先级。CLI 与人工材料冲突时保留双方来源、时间、期间、单位和口径，必要时请求用户确认，不能默默覆盖。解析覆盖按页/表/范围登记；摘要不能替代关键数值和原文。单次提取/传图需要合理大小与时间上限，限制单次工具结果不等于另建上下文预算系统。

### R6 规则替换与既有项目

现有 D-011 保护活动章节，但“后续用新规则”仍可能让同一方案混合不同定义。建议项目固定已激活规则包版本，安装升级只更新可用默认包；已有项目在暂停时明确激活兼容新版，重新校验依赖并标记受影响成果。不要在连续执行中悄悄覆盖 Skill 文件。结构不兼容时拒绝替换并保留旧项目可用，不首版建设通用迁移平台。

开发侧规则梳理工具、交付给用户的运行 Skill、宿主版本分别记录。统一安装不等于一律升级到各组件 latest，使用已联合验收的组合。

### R7 飞书交付失败与本地编辑

现有设计已有目的地确认、回读和远端版本检查，还需确定超时但远端可能已创建、部分块上传失败、附件失败和用户在飞书侧修改的处理。

建议发布固定本地成果快照，保存目标、操作标识与已知回执；状态不明时先核对，不能盲目再次创建。只有正文及必需附件完整且回读符合契约才标为发布成功。远端已有人工修改则停止覆盖并让用户选择处理，不自动双向合并。发布期间本地新编辑不改变正在发布的快照。

### R8 原生接口、编辑能力与干净安装

现有技术草案已标注待验证，不能把候选当能力承诺。优先验证目标 Desktop 的专用 cwd、Skill 发现、同会话续执行/取消、图片传入、成果引用与插件页面入口，而不是先大规模搬页面。

Markdown 是主版本意味着必须先约定可无损编辑的内容范围：复杂表格、合并单元格和特殊附件不能被编辑器静默降级。无法往返的部分保留原件或局部只读，并说明限制。

安装验收覆盖承诺支持的操作系统/架构、依赖获取失败、已有安装更新和卸载保留用户方案目录。不能把开发机全局工具视为用户环境，也不能把知识材料的读取权限当作安装包分发授权。

## 最小验证门槛

1. 一个真实章节：已有材料解析复用、原生生成、提交、预览编辑、同会话修改、用户确认。
2. 三章顺序：缺料不静默跳章，逆序依赖拒绝，修改上游只影响相关下游。
3. 异常：停止后迟到结果、重开恢复、双窗口保存、通用文件外部修改、磁盘写失败。
4. 交付：真实视觉解析、授权后的飞书发布及失败核对、干净聚合安装。

暂不增加数据库、后台任务服务、自动双向同步、工作流画布、并发模型调度或自研模型缓存。

## 本轮证据边界

本轮是本地文档及原型代码抽查，未重新运行功能测试、模型、Desktop 或飞书写入。此前宿主 8/12 测试记录仍是历史证据。本轮外部搜索未返回可用结果，不据此新增官方接口或版本结论。上述建议须在定稿时同步产品设计、技术草案和相关决策，不能只在评审报告中生效。
