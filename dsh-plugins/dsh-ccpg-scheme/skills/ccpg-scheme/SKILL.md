# CCPG Scheme Conversation

Use the CCPG scheme tools when the user expresses an intent to generate, continue, revise, or supply materials for a property-service scheme, service plan, project quality plan, or a matching CCPG business scenario. Natural trigger examples include “生成物业服务方案”, “开始项目质量计划”, “继续下一章”, “我上传了材料”, and “这里有一份飞书材料清单”. Keep execution and material interaction in the current native DSH conversation; the results panel only displays committed artifacts.

- On start, require the current session cwd to be an empty dedicated scheme folder. If it is not, ask the user to switch the DSH session to one empty folder and say start again; do not create or write an outer workspace.
- Accept materials in the form the user provides: conversation attachments, local files or folders, Feishu document/wiki/sheet links, a Feishu list containing multiple links, or data available through verified CCPG CLI. Copy attachments or locally selected files into the initialized project's internal `materials/input` directory with DSH's native file capability. Read authorized Feishu resources through the current-user Feishu capability, then register their fetched snapshots through scheme tools. Never mention the internal directory to the user.
- If a conversation attachment is an archive, unpack it once into the managed input area, preserve the source file names, and register the contained files as individual materials; do not treat the archive entry listing as source content.
- When the user explicitly supplies a Feishu spreadsheet as the actual material list for this scheme (for example, “所有文件都在这个飞书表格清单里”), call `feishu_collect_materials` after initialization. It creates the internal material directory, downloads every linked resource with the current-user Feishu CLI, and saves a local inventory with readable file names. Do not ask for per-file confirmation or write ad hoc shell batch scripts. If exports are pending, resume with the same tool; verified local files are reused. Parse downloaded originals with `material_parse` and bind the completed materials afterward. Report unavailable links or permission/login gaps concisely; never claim the list is complete when the tool reports missing items.
- Links provided only as examples or to describe a future feature are not processing requests: do not read or download them. For an actual non-spreadsheet Feishu document inventory, use `feishu_read`, fetch each referenced resource with the current-user CLI, and preserve its source and completeness. A link title or list row is never the material content.
- Prefer verified CCPG CLI acquisition only when project, permission, fields, period, and metric scope match. Otherwise retain the source as user-supplied material rather than guessing.
- Before relying on CCPG CLI, read [the preparation reference](references/ccpg-cli.md) and check it with `ccpg_cli_status`. Only prepare or update the tool when the user asks or required data cannot otherwise be obtained.
- Use `ccpg_project_find` for project candidates and `ccpg_project_fetch` for an exact project's paginated master-data snapshot. They save current-user provenance and bounded previews locally. Results remain unverified and cannot be bound as completed inputs; a project match alone does not verify field meanings, period or metric scope. Never invent a missing API, silently select another project or treat one page as a complete dataset. Use user-provided materials when the required scope cannot be verified.
- Follow the installed project `AGENTS.md` and chapter skills after initialization. Do not expose internal tool names, skill paths, chapter codes, or material directory paths to the user.
- Load the current chapter's standard Skill from the preparation result through DSH's native skill capability; its relative knowledge, templates and examples belong to that Skill. Keep article openings about the chapter itself, without internal execution explanations, material IDs, paths or Skill names.
- A knowledge inventory, law-name list or summary is not the authoritative original. Resolve only sources needed by the current chapter through available native search/browser tools or the current-user Feishu CLI. Use issuing authorities for laws and verify project jurisdiction, effective dates and applicable clauses. Save originals or faithful Markdown with readable names under `materials/input/knowledge`, retaining URL, retrieval date and version, then parse/register them before preparation and reuse verified sources. Do not claim a search snippet, list or model memory is full text. If tools, permission or original text are unavailable, retain the gap and request the missing source rather than invent retrieval or citations.
- Finish and submit the current chapter before reading later chapters' knowledge or drafting later outputs. Submission failure does not advance the chapter. Preserve its saved body and attachments, correct the tool parameters once, and stop on repeated internal failure without reading plugin source.
- `chapter_prepare` automatically registers and binds declared bundled knowledge originals. If review is required, complete that original once using the returned material ID and paths, then prepare again. Do not ask the user to upload bundled knowledge or register extracted summaries as originals. Use native multimodal capabilities when needed; do not invoke another image service for duplicate verification.
- Before preparing a chapter, parse and register relevant source materials with `material_parse`. Text-only PDF/Office documents complete by extraction. For `needs-review`, use the native file capability and the official `office-docx`, `office-xlsx`, `office-pptx` or bundled `pdf` skill to read the original and resolve relevant content, including comments, tables and business images. Images existing in a document do not require separate visual tasks. For scanned or unreadable content, use the configured multimodal model through DSH's native capabilities only where necessary. Ignore decorative exporter name/time watermarks; preserve business images and the original. Save a document-level interpretation in workspace Markdown and call `material_complete` with its source hash, path, review description and explicit unreadable gaps. Never declare unread business content complete. Reuse the final material ID and Markdown; one original file remains one material. The plugin does not require separate child sessions or a specific image tool. Do not repeatedly attach large images or retry `preflight_compress_failed`; continue from saved state in a clean conversation if needed. Evidence `source` values must be registered material or artifact IDs, never file paths or prose citations.
- Ask one plain-language question only when a required material remains unavailable, and explain blocked chapters by their business gap.
- Required-input enforcement belongs to the plugin's preparation gate, not model discretion. Call the preparation gate before generation; if it rejects a required input, translate that rejection into one concise user-facing request for the missing material.
- Stay in the same conversation to draft each chapter; do not delegate the whole chapter to reread every material and template. Reuse completed Markdown, verified readings and source-backed notes. Read the required knowledge and current output templates; collection templates help material matching or missing fields, and examples are optional expression references.
- Save each completed section immediately to the preparation result's `draftPath` with native file tools. A native `write` call needs both `file_path` and `content`; use native edit for subsequent sections rather than re-emitting the entire draft. Keep reusable exact facts, source IDs/locations, periods, units, unresolved conflicts and completed sections in a short facts note only when useful. Do not prewrite the whole chapter in analysis before writing it again. Resume from the saved draft after interruption.
- Review every declared output, template field, numeric claim, evidence, attachment and gap before submitting. Use `chapter_submit` with `bodyPath` for the saved complete Markdown, plus separate evidence and confirmations; do not copy the whole body into tool parameters. This avoids duplicate generation while preserving all business checks. Human confirmation remains separate.
- Attachments require the exact `id` of a declared attachment in `chapter_prepare.outputs` as `outputId`, a readable `name` with extension, and exactly one of `content`, `contentPath` or `base64`. `contentPath` is a saved UTF-8 md/txt/csv/json file under `materials/notes`. Evidence `source` is a registered material/artifact ID. Never guess these fields or regenerate saved content after a rejected submission.
- When the user requests Feishu creation or clicks the results panel's conversion action, publish the fixed body and every declared attachment into one newly created online folder using their logged-in Feishu CLI. Do not ask for a second confirmation or require a model-turn approval for creation. Keep login, permission, saved-version and snapshot checks; do not switch to bot or another account. Verify the body by read-back, verify each attachment by downloading and comparing bytes, and verify same-folder membership through the current-user CLI. Binary attachments are valid; report a folder link and missing files when only part of delivery succeeds. Overwriting an existing remote document still requires native approval; use creation for complete body-and-attachment delivery.
- If a native scheme tool reports an internal failure, use only its documented recovery once when appropriate. If the same error repeats, stop the current chapter and report the concise error to the user. Do not inspect plugin source, call private HTTP endpoints, or use shell/file tools to bypass the scheme tools.
- When the user says “整理这次测试的问题” or requests a problem report, call `scheme_validation_report` and return the saved local report as a clickable file. It reads recorded issues and structural metadata only; do not reparse materials or start a quality-scoring model.
- Record concise chapter-specific user feedback with `scheme_feedback` and `source: user`; label an unverified model finding `source: model`. Preserve expected versus actual behavior without copying materials, credentials or full conversation. Automatic observations and feedback never approve content, edit rules or change chapter progress. Reports stay local; the user chooses whether to share them.
